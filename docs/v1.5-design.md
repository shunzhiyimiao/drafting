## 1. 为什么做（thesis）

当前 `blueprint/check.rs` 的裁决是**单源**的：把验收标准 + 关联代码丢给模型，模型返回 `[{verdict, suggestion}]`，`CheckVerdict` 取 `Pass / Fail / Unclear`。没有编译信号、没有测试信号、没有结构信号参与。

这正是 spec-driven 卖点里最脆的一环——模型会对**编不过**的代码说 pass，也会对没问题的代码说 fail。用户不会信任一个会幻觉的 pass/fail。

v1.5 的目标：让"代码满不满足 spec"成为一个**可信的、带证据的估计**，而不是一次 LLM 眼判。

**控制论框架**：Blueprint = 参考信号（期望状态），代码库 = 被控对象，裁决引擎 = **观测器**——它融合若干**观测矩阵各不相同**的传感器，重建"满足度"这个不可直接测量的状态。完整自动化（自动再动作）继续 defer 到 v2：LLM 没有传递函数，闭环再动作有振荡风险。

## 2. 传感器模型与融合逻辑（语言无关）

三个信号源观测的是**不同子空间**，噪声特性不同，因此融合是**优先级 + 闸结构，不是加权平均**：

| 传感器 | 观测什么 | 性质 |
|---|---|---|
| **编译 / LSP** | 必要条件（编不过 → 满足度≈0） | 确定性、零幻觉。是**闸，不是票**。对 FAIL 高精度，对 PASS-正确性零信息 |
| **测试** | 行为正确性 | 有覆盖处证据最强；**无覆盖处完全不观测**；红测试 = 硬 fail |
| **LLM 裁决** | 代码是否匹配 prose 意图 | 唯一全覆盖的语义传感器，但高噪声、错误相关 |

**融合规则**：
1. 编译/LSP 是闸：硬错误 → 该 criterion 不可能 pass，直接 fail，诊断即理由。
2. 有映射测试存在 → 测试结果主导（红 → fail；绿 → 强 pass 证据）。
3. LLM 只填**客观手段观测不到的残差**；当它与某个确定性信号矛盾（说 pass 却编不过）→ 那不是 pass，是抓到一次幻觉，**降级为 Unclear**。

**数据模型不用大改**：现有 `Pass / Fail / Unclear` 三值域正好装得下这套——`Unclear` 成为"传感器分歧 / 仅 LLM 有覆盖"时的诚实输出。改的是**裁决产出逻辑**：从「LLM 决定」变成「闸+融合决定」。

## 3. `LanguageProvider` 接缝

裁决融合核**只读语言能力画像、不读具体语言**。每个语言是一个后端实现：

```
trait LanguageProvider {
    fn diagnostics(&self, files: &[PathBuf]) -> Vec<Diagnostic>;   // 经 LSP，协议统一
    fn build_check(&self, project: &Path)   -> BuildResult;        // 编译闸；Python 等可为 None
    fn run_tests(&self, scope: TestScope)   -> TestResults;        // 测试传感器
    fn toolchain(&self) -> ToolchainStatus;                        // 工具链可用性探测
    fn capability(&self) -> CapabilityProfile;                     // 该语言固有可观测画像
}
```

**有效传感器 = 语言固有能力 ∩ 本机已装工具链。** 融合核**绝不报告一个它没真拿到的信号**。

**优雅降级（与 Node/路 B 决策一致）**：缺工具链时，该语言裁决降级为 **AI-only**，明确标注「编译/测试传感器不可用，置信度更低」，并告诉用户「装 X 可升级裁决质量」。Drafting 不打包任何工具链——和我们对 `node` 的处理是同一套：文档化外部前置 + 可操作的报错 + 优雅降级。

**复用已有资产**：`lsp/client.rs` 是语言无关的 LSP 传输（"spawn 给定命令"）；`lsp/manager.rs` 的 server map 已按 `(PathBuf, LspLanguage)` 分桶；`detect_language` 走 `LspLanguage::from_extension`。LSP 这条腿的接缝**已经搭好**。

## 4. v1.5 两个后端：Rust + TypeScript

| 后端 | 编译闸 `build_check` | 测试 `run_tests` | 诊断 `diagnostics` | 当前有效可观测性 |
|---|---|---|---|---|
| **Rust** | `cargo check` ✓ 确定性 | `cargo test` ✓（现有 65 测试） | rust-analyzer（加 `LspLanguage::Rust` 变体 + `.rs` 映射 + spawn 命令） | **三源齐全，最高** |
| **TypeScript** | `tsc --noEmit` ✓ 确定性 | ⚠ **无 runner / 无前端测试** | typescript-language-server ✓ **已接** | **compile + LLM**（测试腿空） |

**两条要注意的现状**：

- **Rust 的 LSP 接入是"一个枚举变体"**：`LspLanguage` 与 `from_extension` 已存在，整套 LSP 子系统已按它参数化。加 `Rust` 变体、`.rs → rust` 映射、rust-analyzer 命令、`languageId = "rust"` 即可。
- **TS 前端目前零测试**（`package.json` scripts 只有 dev/build/preview/tauri）。所以 TS criterion 的 verdict 在 v1.5 起步时由 **compile + LLM** 给出，测试腿留空——这是有效传感器模型该如实呈现的结果，**不是 bug**。
  - *可选 dogfood 增强*（非阻塞）：为前端立一个最小 vitest 套件，让 TS 后端也能跑出真三源。是否做由进度定，不进 v1.5 关键路径。

## 5. S0–S7 构建序列

语言的活**只压在 S4 一步**，其余与语言数量无关。每步收尾以 `cargo test` 绿为准（沿用"最小可编译内核、每步绿"纪律）。

| 步 | 名称 | 语言相关 | v1.5 |
|---|---|:---:|:---:|
| **S0** | canvas↔blueprint 绑定 | 否 | ✓ |
| **S1** | provenance 标记 | 否 | ✓ |
| **S2** | Atlas 上事件总线 | 否 | ✓ |
| **S3** | 只读状态估计器 | 否 | ✓ |
| **S4** | 三源裁决融合 + `LanguageProvider` | **是（唯一）** | ✓ |
| **S5** | 漂移检测 | 否 | ✓ |
| **S6** | operator 反馈面 / 证据轨迹 | 否 | ✓ ← **v1.5 终点** |
| **S7** | 人工门控的再动作 | 是（需 codegen） | ✗ → **v1.5.x** |

**各步产出 / done-when**：

0. **S0 canvas↔blueprint 绑定** — 工件（代码文件/节点）与验收标准建立双向引用。*done*：从一条 criterion 能解析到其关联代码工件集，反向亦可。这是估计器归因信号的前提。
1. **S1 provenance 标记** — 给工件/补丁打来源戳（human / AI / derived），延续 Patchboard 的 `PatchSource`。*done*：任一代码区块可追溯到来源与时机。供 S6 证据轨迹与信任加权用。
2. **S2 Atlas 上事件总线** — Atlas（结构索引）接到 `sync_bus`，结构变化作为事件流出。*done*：文件/符号变更产生总线事件，估计器可订阅。
3. **S3 只读状态估计器** — 订阅总线，维护"每条 criterion 当前满足估计"这一**只读**状态。**只读 = 不触发任何动作**。*done*：任意时刻可查询每条 criterion 的最新估计（此时估计仍可只来自单源）。
4. **S4 三源裁决融合 + `LanguageProvider`** — 引入编译闸 + 测试传感器，与 AI 裁决按观测画像融合（闸→测试→LLM 残差）；`LanguageProvider` 接缝落地，Rust + TS 两后端实现。*done*：一条 criterion 的 verdict 由**有效传感器**融合产出，`cargo test` 绿。**v1.5 核心步。**
5. **S5 漂移检测** — 代码变化使先前 pass 的 criterion 不再满足（或反之）时发出 drift 信号。*done*：改代码后受影响 criterion 的 verdict 自动重算并标记 drift。
6. **S6 operator 反馈面** — 每条 criterion 的 verdict + 证据（哪个传感器给了什么、provenance、drift 历史）呈现给人。*done*：人能在一个面上读到"为什么是这个 verdict"。**v1.5 收在此——人读估计、人手改代码。**
7. **S7 人工门控的再动作（DEFERRED v1.5.x）** — 对 fail 的 criterion，人批准后由 codegen 重新生成代码。**延期原因**：再生成依赖 codegen（TS-only），纳入会把生成侧多语言拽回 v1.5，且破坏 Rust/TS 能力对称。推到 v1.5.x。

## 6. S4 已知风险：验收标准 ↔ 测试 的可追溯映射

测试这条腿要回答"哪个测试对应哪条 criterion"，这是 S4 真正的硬骨头。

**对策：先粗后细，别让 S4 膨胀。**
- **v1.5（粗）**：按**模块粒度**归因 pass/fail（Rust 单 crate，归到 `blueprint` / `patchboard` 等模块；TS 归到视图/目录）。先能发。
- **v1.5.x（细）**：细到单条 criterion ↔ 单个测试，作为后续 refine。

## 7. v1.5 验收闸：dogfood 自身

S6 完成时，**让 Drafting 用自己的 Blueprint 验证自己的 Rust + TS 代码**——零假设的端到端验证。

预期结果（且应被如实呈现）：
- **Rust criteria** → 拿到完整三源 verdict（cargo check + cargo test + AI）。
- **TS criteria** → 拿到 compile + AI（测试腿空，除非做了可选 vitest 增强）。

这恰好检验"有效传感器"模型在"某腿present-but-empty"时是否诚实降级——是 v1.5 架构正确性的活体测试。

## 8. 明确不做（v1.5 之外）

| 项 | 去向 | 原因 |
|---|---|---|
| 生成侧多语言（codegen 出 Rust/C#/Python/C++/Java） | v2 独立线 | 模板 × 语言组合 + 逐语言 adapter 保护，另一头野兽 |
| C# / Java / C++ / Python **验证**后端 | v1.5.x / v1.6 串行铺 | 各语言可观测性与工具链供给难度差异大，在跑通的接缝上逐个加 |
| **S7** 人工门控再动作 | v1.5.x | 依赖 TS-only codegen，破坏语言对称 |
| 完整自动化（自动再动作闭环） | v2 | LLM 无传递函数，振荡风险 |
| 旧「留 v1.5」功能桶（Atlas Reference/Module Map、GitHub API 集成、Vim/Emacs keymap、完整 hunk 级 Adapter 保护、终端内嵌 AI、更多 provider、blame 面板……） | backlog，待单独 triage | 与回路闭合 thesis 无关，不在 v1.5 承诺内 |

**后续验证后端的推荐顺序**（在跑通的 `LanguageProvider` 接缝上）：
C#（编译闸干净，.NET SDK 供给）→ Java（Maven/Gradle 构建系统 + classpath）→ C++（最硬：依赖 `compile_commands.json`、工具链各异、clangd 准度取决于构建配置）。
**Python 可提前**（第二个）：它无编译步骤、客观可观测性最低，是"某传感器干脆不存在"的**诚实压力测试**，在 C++/Java 的构建地狱之前先验证退化路径。
